# Deployment, backup, and operations

## Environment

Copy `.env.example` to `.env` and configure:

| Variable | Purpose |
|---|---|
| `NODE_ENV` | Use `production` for deployment |
| `DEMO_MODE` | Set `true` only for local, loopback-only demo use; set `false` for any deployment |
| `HOST`, `PORT` | Bind address and port; loopback is the local default |
| `DATABASE_URL` | Private PostgreSQL connection string; never expose to browser |
| `SESSION_SECRET` | Required outside demo mode; at least 32 random characters |
| `DASHBOARD_PASSWORD_HASH` | Required outside demo mode; bcrypt hash generated by `npm run password-hash` |
| `SESSION_COOKIE_SECURE` | Must be `true` in production behind HTTPS |
| `TRUST_PROXY` | Set `true` only behind a trusted reverse proxy |
| `MAX_UPLOAD_BYTES` | Upload limit; defaults to 5 MiB |
| `REPORTING_CURRENCY` | Display preference only; never overrides imported row currency |
| `PGSSL` | Set `true` if the PostgreSQL deployment requires verified TLS |

Do not pass passwords in command arguments or commit `.env`. Rotate the password by generating a new bcrypt hash and updating the server environment. Restart the application to apply it.

Local `DEMO_MODE=true` skips sign-in and CSRF checks only outside production. Requests are restricted to loopback and the server only accepts a loopback bind host. This mode is for local development/demo data only; never expose it on a LAN, public host, or reverse proxy. Production startup fails if demo mode is enabled.

For a frontend-only preview without Node.js, npm, or PostgreSQL, run `python demo-server.py`. It binds to `127.0.0.1:8000` and serves only the allowlisted UI and clearly labeled tenant-snapshot showcase records. It does not expose repository files or connect to a database.

## Initial setup

1. Install Node.js 20+ and PostgreSQL 14+.
2. Create a private database and a dedicated application role. Restrict network access to the application host.
3. Configure `.env` with `DEMO_MODE=false`, production credentials, and install the pinned npm dependencies (`npm install`).
4. Apply the versioned schema using `npm run migrate`.
5. Start with `npm start`; check `/health`. For local demo, open `/`. The current frontend intentionally has no sign-in screen, so a non-demo deployment needs a client that obtains the authenticated owner session before opening the dashboard.
6. Configure HTTPS termination before exposing the service outside loopback. Set `SESSION_COOKIE_SECURE=true`; set `TRUST_PROXY=true` only when the trusted proxy is configured to overwrite forwarding headers.
7. Keep the application behind a private network/VPN or equivalent access control. There is one owner account and no registration.

The server intentionally serves a file allowlist rather than the repository root. Do not deploy the repository through a separate static file server: the repository contains tenant source data and development artifacts.

## Database permissions

The application currently needs SELECT/INSERT/UPDATE on dashboard and import tables, session table access, and migration DDL during setup. In production, apply migrations with a separate migration role, then restrict the runtime role to necessary CRUD privileges. Keep PostgreSQL off the public internet and enable encrypted connections where supported.

## Backups and recovery

- Schedule encrypted `pg_dump` backups outside the application host. Protect backup files and test restoration regularly.
- Example backup: `pg_dump --format=custom --no-owner --file=dashboard.dump "$DATABASE_URL"`.
- Restore to a new/empty database first: `pg_restore --clean --if-exists --no-owner --dbname="$DATABASE_URL" dashboard.dump`.
- Keep original import files under the organization's approved retention and encryption policy; the database tracks file names and hashes but does not archive original files.
- After restore, run `npm run migrate`, start the service, verify the authenticated dashboard and import history, and compare record counts/currency balances to the backup manifest.

## Troubleshooting

- `DATABASE_URL is required` / connection refusal: verify server-only environment and PostgreSQL access.
- `DASHBOARD_PASSWORD_HASH` or session-secret startup error: set the required values; do not use a plaintext password as the hash.
- Missing `user_sessions` or schema tables: run `npm run migrate`.
- Login works but later API calls fail: inspect session-table access and cookie HTTPS/proxy settings.
- Import reports rejected rows: open **Import history → View rejected rows**. Fix the source file and re-import; existing records are not overwritten.
- Multiple currencies require a selection; no automatic conversion is applied.
- POS/billing refresh returns connector unconfigured: provide authorized API/database docs, exact field mapping, change cursor, test access, and credentials through deployment secret storage. Do not put credentials in this chat, frontend config, or source files.

## Limitations

No hosting provider, operational source, source credential, schema, approved exchange rate, or actual financial dataset was available during implementation. Automated POS/billing synchronization, retry/backoff, reconciliation against source totals, backup execution, and production HTTPS setup remain deployment/source-owner work. Do not describe the dashboard as live until a source adapter has passed authenticated integration and reconciliation tests.
